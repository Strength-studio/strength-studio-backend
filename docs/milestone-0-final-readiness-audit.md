# Strength Studio Milestone 0 final readiness audit

**Scope.** Read-only comparison of the nine Milestone 0 documents, including both ERD panels and the deployment diagram, against the original business report and deployment blueprint already reviewed. The workspace contains documentation only and Git is uninitialized. This report is the only new artifact. Database races were walked through conceptually. No SQL, security tests, deployment, or VPS measurements were run.

**Verdict.** Retain the modular monolith, PostgreSQL/Prisma, Flutter, Next.js on Vercel, and the single Hostinger worker. The architecture can meet the confirmed requirements. The documents still need binding rules for identity and revocation, write retries, scoped relationships, and shared transaction semantics before Foundation starts. The report proposes corrections without changing approved requirements or deciding studio policy.

**Finding convention.** Critical means a correctness or privacy defect with a concrete failure mode. High means an affected workflow or release gate would be unsafe or underspecified. Medium and Low mean a narrower or deferrable issue. The gate column states when resolution is required.

## Financial and entitlement trace

1. **Record → verify → fund.** A manual receipt stores immutable reported facts. A correction before verification supersedes it. Lock the finance account and receipt, validate source identity and current state, then create one cash-backed lot, one origin event, and the set-once verification pointer. Only origin and receipt-correction events affect verified cash. Allocations change where money is applied and do not increase cash collected. A01, A03–A04, B01–B02 remain necessary controls.
2. **Fund → allocate → settle.** Lock the account, check the source bucket net of active reservations and the target's remaining balance, then append the allocation. One lot can cover several installments and an installment can receive several lots. Compute each installment from its scheduled amount less net targeted allocations. Compute purchase balance from charges and adjustments less all net allocations once. Include installment allocations in that purchase total exactly once. Compare receipt, lot, purchase, and installment scope before posting.
3. **Settle → activate.** Lock the same account before the target membership. Compute net eligible verified cash-backed allocations for the applicable purchase or approved item scope. Unapplied money and an unrelated receipt do not qualify. The authorized activation transaction records its policy and evidence, sets validity, and posts the purchased session grant once. The alternative is a reasoned Admin exception, never a staff override. A payment event cannot activate on its own.
4. **Refund → reversal → reconcile.** Reverse allocations explicitly when needed and return funds to their original buckets. Reserve against the chosen bucket and original receipt in the approval transaction. Available bucket equals its signed event balance less active reservations. Cumulative posted cash refunds plus active reservations must fit the verified receipt net of valid receipt reversals. Claim execution once. An ambiguous payout remains reserved. On confirmed execution, record one cash-return event and release the matching reservation atomically. Never reverse a real cash movement without evidence. Rebuild balances from events and reconcile reserved cases separately. Refunds do not silently alter memberships or restore consumed units.
5. **Terms → validity → verified use.** Publish package fields and eligible session types under the package lock. Record the requested version and immutable purchase-item terms. Evaluate formal validity, explicitly authorized grace, suspension/cancellation, and units independently. A session debit is an append-only result of accepted Admin verification. An authorized grant or adjustment has its own source. Use `UQ(revision_id)` on verification and `UQ(verification_id)` on entitlement entries. Lock the membership and attendance before deriving the correction delta. A returned correction has no effect. A refund's entitlement review is independent and membership-scoped.

## Scheduling race walkthroughs

Use one short READ COMMITTED transaction per command, fresh reads after locks, and a time sample after lock acquisition. The proposed order for scheduling is stable policy row if needed, then coach, client, membership, slots by ID, then booking/change rows. Revalidate the affected IDs. All seat or assignment writers use the same protocol. A CHECK constraint cannot enforce a cross-row seat count. [PostgreSQL constraints](https://www.postgresql.org/docs/current/ddl-constraints.html), [explicit locking](https://www.postgresql.org/docs/current/explicit-locking.html)

| Race | Required mechanism and expected result |
|---|---|
| Two clients request the last group seat | Each request takes the same slot row lock before counting confirmed bookings and live holds. The first writes and commits. The second recounts and receives `SLOT_FULL` or joins an approved waitlist with no seat. Use partial UQ active slot/client and IX slot/state/expiry. Capacity reductions take the same lock. |
| Two Admins approve overlapping coach reservations | Lock the coach and affected slots. Verify availability. Use partial UQ active reservation per slot and GiST exclusion on equal coach and overlapping active buffered `tstzrange(..., '[)')` with `btree_gist`. Only one overlapping assignment can commit. Touching ranges can commit if the agreed buffers allow it. |
| Reschedule competes with a target-slot request | A pending reschedule holds no replacement by default under the proposal. At approval, lock original and target slots in ID order, recheck the original is still confirmed, and count the target. Update the participant and decide the change together. If the target was taken, the original remains confirmed. UQ one pending change per participant and active slot/client still apply. |
| Approval races an expired hold | Lock the same slot and participant as cleanup. Capture actual post-lock database time. A hold at or past expiry cannot be approved and does not count toward capacity. Mark the same client's stale active hold expired under lock before a replacement insert that would hit partial UQ. |
| Coach becomes unavailable after confirmation | Approval of unavailability locks the coach and affected slots, records the window, and flags affected slots. A competing booking approval rereads after locking. If it commits first, the booking stays confirmed and is flagged for review. If unavailability wins, a new conflicting approval fails. Reassignment releases and creates reservations atomically. Historical attendance attribution remains unchanged. |

## Security and KVM1 release evidence

The proposed separation of Admin, Staff, Coach, and Client is sound **subject to A01–A02 and A06**. Test Staff with every grant and each grant in isolation. Test coach access against another coach's service assignment and client access against another client's IDs, lists, exports, and notifications. For commission tests, seed distinctive private identifiers and amounts. Probe every ordinary query and output path and check worker and database credentials directly. Include revocation between export creation and download, permission removal on an existing socket, stale bearer requests, and failed-auth logs.

The five memory caps total **2,304 MiB**. Adding the proposed 1 GiB host allowance brings the planning total to **3,328 MiB**, before verifying actual usable RAM or the peak cost of one-shot work. This is a budget, not a measured capacity result. The one CPU can saturate while memory remains available. Confirm cgroup limits, disk headroom, DB connection use including the private pool and maintenance tasks, and actual Vercel/VPS routing.

Use an external load generator against equivalent 1-vCPU/4-GB resources or the purchased VPS in an approved window. Seed representative finance and booking history. Exercise simultaneous login and hashing, reports, last-seat writes, Socket.IO clients, and worker delivery. Run sustained peak, burst, and soak. Include a backup, AOF rewrite, Redis loss, and worker restart. Observe p95 latency and errors, CPU and steal, cgroup memory and OOM, swap pressure, database waits, WAL and disk growth, and outbox recovery age. Agree the thresholds before the run.

Before release, test Nginx/TLS renewal, SMTP, and isolated restoration from encrypted off-server storage. Restore with external delivery disabled, verify grants and constraints, reconcile ledger totals and unknown payouts, rebuild pending jobs with empty Redis, and record achieved RPO/RTO. Simulate snapshot recovery after a session revocation and payout to verify cutover procedures. Backup retention and launch targets remain studio decisions.
