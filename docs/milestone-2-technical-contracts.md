# Milestone 2 technical contract review

10 November 2026. The [decision register](milestone-2-decision-register.md) records owner approvals. The designs below are proposals for review before the first Milestone 2 migration. Foundation is the runtime baseline.

## Receipt identity and duplicate prevention

**M2-T01 / B01.** One receipt root represents one observed physical movement. Evidence references identify proof shared outside the application. Some also identify the physical movement within a verified issuer namespace. Store the evidence and identity separately.

| Method or evidence | Candidate identity and example |
|---|---|
| Cash with a controlled receipt | Use the studio issuer and receipt series plus receipt number. `front-desk / 2026-A / 0042` is distinct from another series using `0042`. A centrally issued number works only when staff reuse it for the same physical handover. |
| Bank transfer | Use the bank or payment rail and a stable receiving account ID plus the issuer transaction ID. Include additional documented scope, such as a statement or date, only if the issuer reuses IDs in that scope. `bank-A / account-1 / ref-77` and `bank-A / account-2 / ref-77` may be distinct. Two client records quoting the first identity refer to the same movement. |
| Manual terminal or wallet settlement | Use a validated provider/merchant namespace and transaction ID. For a short terminal reference, include terminal and batch or business date only if the provider defines those as part of the identity. A Mada slip or STC Pay message can be evidence even when its short reference cannot safely deduplicate. |
| Missing or ambiguous reference | Record a provisional receipt with a durable intake ID. Check for likely duplicates using account/terminal, amount and time as review signals, never as a unique key. Admin must record the missing-reference exception, how the movement was verified and the duplicate check or disposition. Reuse the intake ID when available. Keep unresolved candidates nonspendable. Two independently reported receipts with no shared identifier cannot be guaranteed to represent distinct movements. |

Normalize per issuer without dropping meaningful zeroes, case or separators. Preserve a safe original reference. Never include client, amount, payment-method display name, or a configuration version in a physical identity key. Map equivalent method aliases and versions to the same verified namespace. If a namespace or uniqueness guarantee is unknown, use provisional intake and review until it is verified. Review the scope and normalization fixture set for each enabled method. Historical payments retain their method version.

Reserve a strong identity on **recording**, before creating a second payment root. Proposed unique constraint on a receipt identity claim `(namespace_id, normalized_identifier)`, with both components required and the claim linked to one root. Support additional claims linked to the same root when evidence improves. Use a unique intake ID for a provisional root, never an empty or shared placeholder identity. Keep one effective authorized origin per root through a guarded root pointer plus uniqueness on the origin event per authorized revision. Scoped keys bind receipt revision, account, currency and root. The global identity must survive cross-client duplicate attempts and audit retention.

In one short transaction recheck actor/action and claim the request key. Acquire the known finance account, claim identity under the unique constraint, then insert root and immutable recorded facts. A duplicate insert waits on the unique index and loses with a scoped conflict, unless it is the same authorized idempotent replay. Cross-client conflict responses disclose no client or payment details. Root locks serialize verification, authorization and corrections. For provisional intake, use the same root lock on retry and review likely competing provisional roots before authorization. When a strong identity arrives later, claim it under lock. On conflict keep the candidate nonspendable and require Admin reconciliation. No command discovers and acquires another account after taking its first receipt lock. Multi-account repair would require a separately scoped, sorted lock set.

A correction adds a revision or linked compensating transaction, with a reason and an explicit original. Keep identity claims even after rejection or reversal, so new request keys cannot resurrect the same movement. A corrected reference can add a verified alias to the root. A genuinely different payment requires its own root. Replace an effective authorization only after resolving dependent allocations, credits, refund holds and payouts. A correction that lacks sufficient evidence stays pending and posts nothing.

Closure evidence includes simultaneous recording with distinct keys/clients for one strong identity, reused references in different namespaces, duplicate intake retry, later alias collision, and correction/reversal without losing root uniqueness. Review unique-constraint conflicts and lock order on PostgreSQL 17. [PostgreSQL constraints](https://www.postgresql.org/docs/17/ddl-constraints.html) · [PostgreSQL locking](https://www.postgresql.org/docs/17/explicit-locking.html)

## Financial ledger and event effects

**M2-T01 / B02.** Use immutable, typed entries and the same finance-account lock for all balance writers. Keep workflow transitions distinct from financial postings. All commands recheck action, resource and state under lock, including on replay. Scope HTTP keys by actor and canonical operation, and hash normalized input including IDs and amount. Persist the successful outcome and audit atomically. The durable key in each row also prevents duplicates under a new or expired HTTP key. Every audit includes actor or system attribution, time, action, target, correlation ID, and safe evidence and reason where applicable. The symbols below are proposed event names.

| Operation and source | Authority | Effect and entry | Reversal | Durable identity and audit detail |
|---|---|---|---|---|
| Record receipt revision | Admin or Staff with `payment.record` | No balance effect. Append RECORDED workflow event. | Correct or supersede by authorized history. | Root identity and revision. Capture recorder, method, amount and evidence reference. |
| Verify recorded revision | Admin or delegated Staff with `payment.verify` | No balance effect. Append VERIFIED_AWAITING_AUTHORIZATION. | Return/reject by explicit decision, preserving verification. | At most one current verification for a revision/cycle. Record verifier and time. Admin may verify their own recording. Staff self-verification remains open. |
| Authorize verified revision | Admin with proposed `payment.authorize` | `PAYMENT_ORIGIN` adds authorized cash and creates one lot in UNAPPLIED. Record Admin review and authorization separately from verification. | Authorized source-linked correction only. | One origin per authorized revision and one effective origin per root. Preserve distinct recorder, verifier, reviewer and authorizer/timestamps even for the same Admin. |
| Allocate/reallocate authorized lot | Admin with `payment.allocate` | `ALLOCATE` moves UNAPPLIED to an exact purchase and optional installment. Reallocation atomically reverses identified old lines and adds explicit new lines, with source/target caps. | `UNALLOCATE` links original, restores its original bucket and increases the outstanding balance by reducing settlement. | Command and per-line durable IDs. Record old/new targets and reasons for reallocation. |
| Create credit from eligible overpayment | Trigger pending O-04 | `CREDIT_CONVERT` moves UNAPPLIED to CREDIT within the same receipt lot. Cash and receivable unchanged. | Linked reverse conversion up to available, unreserved remainder. | Unique conversion decision/line per source. Record trigger, source and amount. |
| Apply credit | Admin with proposed `credit.apply` | `CREDIT_APPLY` moves CREDIT to an explicit purchase/installment. Decrease credit and increase settlement once. | `UNALLOCATE` restores original credit lot. | Durable allocation line ID. Record lot, destination and amount. |
| Adjust credit | Admin with `credit.adjust` | `CREDIT_INCREASE` creates traceable manual credit or compensates a linked prior decrease. `CREDIT_DECREASE` debits an available lot. Preserve cash backing as described below. No cash receipt, refund or revenue. | Linked compensating event, capped at source remainder. | Unique adjustment and source line. Record reason, actor and provenance. |
| Request and authorize payment correction | Staff with proposed request grant may request. Admin initiates and authorizes with `payment.reverse`. | Request and initiation post nothing. Authorization appends required `UNALLOCATE`, credit reversals, `ORIGIN_REVERSAL` and any authorized replacement origin. Resolve active refund holds and actual payouts before reversing. | A later explicit correction compensates prior effects. An actual cash payout uses refund reconciliation. | One authorized outcome per correction and one durable key per derived entry. Audit original, reversal, replacement, reason and evidence. |
| Approve refund against eligible source | Admin with `refund.decide` | Reserve fixed lot/bucket and amount. Reduce spendable funds. Cash, credit ledger totals and receivable charges remain unchanged. Any preparatory unallocation is separately authorized and posted. | Release an unexecuted or proven unpaid hold. | One approval reservation per case. Audit source, amount and reason. |
| Execute and confirm refund | Admin with `refund.execute` and `refund.post` or `refund.reconcile` for respective actions | Claim posts no cash. Confirmed payout posts `REFUND_PAID`, debits source bucket, records cash out and releases proven resolved hold. | Confirmed returned payout appends `REFUND_RETURNED` and restores original bucket/eligible source capacity. | One live claim per case and one confirmed payout per claim. Scope external evidence identity to its issuer where deduplication is reliable. Audit execution and actual movement separately. |
| Record initial receivable or adjust it | Formal acceptance uses proposed `purchase.accept_record`. Separate Admin-only adjustment with reason. | Positive acceptance posts `PURCHASE_CHARGE` once. `RECEIVABLE_ADJUST` changes the contractual obligation only, scoped to purchase and relevant installment(s). Cash and settlement unchanged. | Linked adjustment with caps. Avoid obligation below net settlement and keep installment totals consistent. | One initial charge per purchase. Unique adjustment and lines. Audit reason and before/after obligation. |
| Cancel purchase | Admin with proposed `purchase.cancel` | Append cancellation event. Preserve original contract and usage. No cash, credit or settlement posting. Route any approved receivable or service effects through separate decisions. | No silent re-open. Any later business workflow needs explicit policy. | One terminal cancellation per purchase. Audit reason and separate review links. |
| Accept SAR 0 purchase | Admin with purpose and required agreement evidence | Freeze normal terms and issue pending membership. No positive receivable, payment origin or revenue. | Reasoned Admin cancellation; keep original agreement. | Same acceptance uniqueness as positive purchase. Audit purpose, terms and acceptance evidence. |

### Balances and database invariants

- Enforce closed per-kind required and forbidden references. Pair every reversal with original kind, amount, lot, source bucket and scope. Cash lot requires an authorized payment. Manual credit requires an Admin adjustment source. Distinguish reservations and workflow events from postings. Validate `amount > 0` and proposed SAR input precision of two fractional digits, store exact decimals, and review the precision contract before schema approval.
- Unapplied and credit ledger balances come from typed postings. Subtract active holds to derive **spendable** amounts. Cap aggregate settlement by target obligation and aggregate debit by source balance. Use account/currency and scoped FKs to purchase, installment, receipt, lot, refund and original event. Under account lock, re-read after waits. Database unique and row-local checks supplement the locked aggregate validations. Runtime roles cannot update or delete financial facts or audit.
- Outstanding purchase balance = contractual charge plus signed receivable adjustments minus net explicit allocations. An installment's allocations also belong to its purchase and count once. Sum installment obligations to the purchase obligation for a fully scheduled purchase. Only positive effective allocations of authorized payment or credit to the purchase count as its funding. An earmark, refund hold or unallocated receipt contributes zero.
- Cash-backed lot conservation = authorized principal minus origin corrections and net confirmed payouts, equal to its unapplied, credit, applied and restricted residual amounts. A reasoned decrease of cash-backed credit moves value to a proposed nonspendable residual bucket, so it does not silently reopen funds or imply cash moved. An explicit linked compensation restores credit. Review any other disposition separately. Reconcile manual credit as a separate provenance class from adjustments, allocations, linked compensation and any permitted payout. A manual-credit payout requires the owner’s O-04 source clarification. A future manual-credit payout would be a studio cash outflow, never a fabricated payment return.
- For example, authorize SAR 120, allocate SAR 60 and 40 to two installments, and leave SAR 20 unapplied. Before authorization the same receipt provides SAR 0 spendable. If an Admin separately unallocates SAR 10 to fund a refund, settlement falls to SAR 90 and outstanding rises by SAR 10. A confirmed refund of SAR 30 consumes the unapplied 30 and changes cash, while the contractual installment charges stay fixed. A separate SAR 10 receivable reduction changes what is owed once and posts no cash.

Before migration review, write the exact kind/reference/nullability matrix, scoped indexes, lock-target permissions, posting identities and independent reconciliation queries. Test concurrent allocation, reallocation versus activation, duplicate origin, refund holds versus credit spend, and credit restoration. PostgreSQL check constraints validate a row, while cross-row balances need the guarded write path. [PostgreSQL constraints](https://www.postgresql.org/docs/17/ddl-constraints.html)

## Refund execution and reconciliation

**M2-T01 / M2-T04.** Use the same case states for a receipt refund and a cash-backed credit refund. A refund case references its authorized payment and a fixed eligible source lot/bucket. For multiple roots, propose source-scoped cases linked by one review/correlation ID, with explicit amounts per root. The case for manually created credit remains gated pending the O-04 linkage decision.

| Transition | Proposed contract |
|---|---|
| REQUESTED → REJECTED or APPROVED_RESERVED | Owner-client can request an eligible receipt refund or Admin acts on behalf. Admin-only for credit cash-out initiation/authorization. Under lock re-read available balance and cap cumulative payouts plus holds against effective refundable receipt principal, accounting for proven returns. Reserve source, amount and reason. Approval is neither a payout nor evidence of cash movement. |
| APPROVED_RESERVED → EXECUTION_CLAIMED | Admin claims one execution before moving money externally. Persist token, intended method, actor and time. Same-key replay returns prior outcome and never issues a fresh payout instruction. Unclaimed approval may be voided by Admin with reason. |
| EXECUTION_CLAIMED → POSTED or RECONCILIATION_REQUIRED | Confirm actual amount, time and reference to payout, linked to refund and original payment. Use a reasoned Admin evidence exception when the reference is missing. Keep proof outside the application. Atomically post confirmed cash, debit lot/credit and release only the resolved hold. Ambiguity leaves funds reserved and prevents retrying payout. |
| RECONCILIATION_REQUIRED → POSTED, PARTIALLY_POSTED, or FAILED/VOIDED | Admin reconciles against external records. For a proven partial payout, post actual within cap and release only the proven unpaid remainder. When the outcome is still uncertain, retain the hold, record observed versus disputed amounts as evidence, and wait for a resolved actual amount before the terminal posting. No further cash attempt. Proven nonpayment releases hold and records failed/voided history. A subsequent attempt requires a new authorized case referencing the resolved one. Unexpected overpayment is an incident requiring reconciliation and a separately controlled adjustment. |
| Confirmed payout returned externally | Preserve the original payout. Require external return evidence and Admin authorization, append a linked compensating cash and source-lot entry, and cap by actual unreturned payout. A refund reference correction alone posts no cash. Never reopen purchase allocations or service automatically. |

The receipt's payment, lot, refund and evidence must resolve to the same scope. Distinguish `requested`, `approved/held`, `executed/claimed` and `confirmed paid` in every read and report. A credit hold lowers available credit at approval, and confirmed execution records the linked ledger debit exactly once. For partial execution, propose one terminal net confirmed payout posting per execution claim once the outcome can be fixed. Track intermediate evidence and outstanding reservation until the result is known. A later refund is a separate case. Provider and worker retries never execute external money movement.

A refund may require a separately posted unallocation. It never automatically reduces installment charges. A service review references its refund, funding correction or cancelled purchase and affected membership. Admin explicitly decides membership and remaining units independently. A no-change outcome is auditable. Freeze decision/application identity so retries cannot double-adjust units. Resolve ambiguous execution, restoration of the exact source bucket and concurrent claims with state-machine and independent balance tests before exposing refund actions.

## Private catalog and offer privacy

**M2-T02 / B05.** Keep private identity client-owned. Freeze owner and visibility upon issuance. Published commercial fields and eligible services are immutable. Edits create and issue a new version under the offer lock, superseding the old for acceptance. An offer without an expiration remains eligible until superseded or withdrawn. A public catalog successor or archive must not silently reprice, repoint or withdraw an already issued private offer. Store exact immutable reference terms or a complete private snapshot when issuing. Accepted purchases freeze the complete agreed terms independently of catalog state.

- Use same-parent version keys and a unique current-issued version per offer. Scope acceptance evidence, request and purchase to the exact client and version through composite keys or a locked relationship check. A private accepted agreement cannot be withdrawn. Resolve private offer reuse before deciding whether to enforce one accepted purchase per offer root. Public version reuse is separate.
- Apply owner predicates in SQL for all Client list/detail/acceptance routes. Do not accept a caller-supplied owner as authority. Admin/Staff management uses the dedicated private management action and its scoped projection. Payment verification and ordinary catalog reads provide no management access. Admin withdrawal requires an unaccepted offer and a reason. Staff withdrawal remains outside the proposed binding pending clarification. Privileged histories use management scopes. Cross-client requests do not reveal existence, pricing or evidence through errors, search, cache, logs or replay.
- Explicit Client confirmation is a separate agreement evidence action, bound to exact terms and client identity. An intent request alone is insufficient. For signed evidence record a safe reference, and for verbal agreement record a supporting note and responsible operator. Record method, evidence time, formal acceptance timestamp and actor. Capture the exact terms the evidence covers. Freeze evidence and snapshot on acceptance. Apply role- and owner-scoped output and redact evidence from unrelated reads.
- Under a consistent finance account and offer/version/request lock order, formal acceptance rechecks ownership, current eligible version, withdrawal, expiry and agreement evidence using post-lock time. Then atomically writes accepted state, snapshot, pending membership, and any charge. A competing edit or withdrawal wins first or loses against the committed acceptance. Replays cannot accept twice or disclose another client's terms. Use one durable purchase per intent, and separately review any assisted acceptance identity needed when no Client intent exists. Backdate neither version validity nor evidence to bypass expiry.
- Exercise acceptance at expiry, two different keys accepting one intent, revocation while waiting, Staff without the dedicated grant, and withdrawal or supersession versus acceptance. Review the query scope and exact composite keys before catalog migrations.

## Purchase and membership transitions

**M2-T02 / M2-T03 / M2-T04.** Use separate purchase, membership and financial state. Names below describe logical states and effective projections. Review which fields need stored status versus derived state before designing persistence.

| Aggregate or transition | Proposed guard, effect and history |
|---|---|
| Purchase intent → SUBMITTED | Client may submit own intent for an eligible offer. Assisted intent uses an explicitly authorized path. Capture exact version and optionally evidence by a separate action. Client may withdraw own pending intent. Authorized review may reject with reason. These actions create no receivable or entitlement. |
| SUBMITTED → ACCEPTED_RECORDED, or assisted formal acceptance | Admin or Staff with dedicated proposed `purchase.accept_record` verifies eligible exact terms and valid agreement evidence. Atomically record purchase, snapshots, acceptance history, any positive charge, installments and PENDING_ACTIVATION membership. Neither general recording nor review substitutes for dedicated authority. SAR 0 remains Admin-only. |
| Purchase RECORDED → CANCELLED | Admin only with reason, including after service use. Preserve contract, installment, payment and usage history. Cancel never implies termination, credit change or refund. Determine any receivable change through separate Admin adjustment under the owner’s cancellation policy. |
| Membership PENDING_ACTIVATION → ACTIVE or SCHEDULED_START | Admin only. Lock account then membership and evaluate exact net purchase funding, including allocated credit. Preserve evidence IDs, evaluated amount, policy, activation instant and effective Riyadh start date. Support approved partial funding, SAR 0 purpose, or separately gated Admin exception. Validate the selected start against frozen terms. Append activation and at most one initial session grant. A future grant is effective only at start. |
| SCHEDULED_START → ACTIVE | Eligibility begins at the effective boundary without a second Admin approval or grant. Derive from persisted bounds and current time. A system event, if persisted, has a unique transition ID. Changes in funding after approval create a separate Admin review where applicable, without implicitly moving the start or applying service effects. |
| ACTIVE → scheduled or open-ended suspension | Admin records reason and local start and optional end. The proposed interval is half-open and blocks use at its start. Preserve independent validity. Reject empty/reversed intervals and competing suspension windows unless an explicit amendment workflow is approved. |
| Scheduled suspension → effective ACTIVE | At configured end, resume automatically if validity and other lifecycle restrictions permit. Query-time eligibility uses the interval, and any system history is posted once with distinct effective and processed times. Expiry or termination wins over resumption. |
| Open-ended suspension → effective ACTIVE | Admin explicitly reactivates and closes the interval. Preserve reason and actor. Reactivation never extends validity. If expired, reactivation alone grants no access. |
| Extend validity | Admin appends reasoned extension without new payment or grant. Preserve original expiry, old and new dates, and any already expired interval. Proposed post-expiry extension resumes eligibility prospectively from authorization, without backdating historical bookings or deductions. Respect ongoing suspension and terminal termination. |
| ACTIVE → TERMINATED | Admin can terminate early, with a reasoned event and preserved history. Purchase, finance and remaining sessions require separate decisions. Terminal state blocks all future eligibility. |
| Expiration and unused entitlement | Expire at exclusive end. Derive eligibility and unusable units from database time and immutable bounds/history. Preserve unused units for audit. No grace, silent debit, or automatic extension. An explicit eligible extension can restore use of remaining units within the newly effective interval. |

A cancelled purchase and a terminated membership are separate states. For a never-activated membership, the proposed guard rejects ordinary activation against a cancelled purchase pending a separate Admin service decision. Serialize cancellation and activation on the account, purchase and membership. If activation commits first, preserve its recorded start and funding, and require explicit Admin review of service consequences. Keep any pre-start revocation or rescheduling outside the proposed commands until its business rules are defined. Evaluate funding and post the initial grant under the same locks. A concurrent reversal or reallocation sees the committed activation and can open a review, or wins first and activation sees updated funding. Compare the planned start, suspension boundary and expiry using one fresh time sample after locks. Reject stale or invalid transitions and retain previous state. Test concurrent activation, extension versus expiry, termination versus scheduled reactivation and grant retries. Future attendance posts only to the selected membership after Admin verification.

## Authorization and O-15 reconciliation

**Blocked by an architectural/security conflict.** The policy is approved. Both ordinary and exceptional activation are Admin-only. The Foundation baseline authorized a Staff grant for the ordinary stub. The public catalog release denies legacy grants at runtime and rejects new assignments. Both stubs remain disabled. The [runtime evidence inventory](milestone-2-readiness-review.md#o-15-authorization-conflict) traces persisted Prisma/SQL vocabulary, the grant writer, action map, guard and session checks, command service, tests, and OpenAPI.

1. Future change makes `membership.activate` and `membership.activate_exception` Admin-only at the map and at command/replay time under the current-role lock. Keep separate input and evidence contracts. Deny old grant values from ordinary authorization immediately on the compatible release.
2. Remove the legacy Staff value from assignable permissions and reject new grants. Use an audited retirement/revocation path for existing rows and invalidate affected sessions/socket authorization after commit. Keep the enum value as a compatibility tombstone until every relevant binary tolerates the transition. Retain original grant/audit history and the historical Foundation migration. Do not expose activation while an old binary can still authorize a Staff request. Apply the same grant-issuance and denial discipline to legacy `payment.allocate`.
3. The proposed dedicated `purchase.accept_record` action does not confer activation, and `catalog.private.manage` does not confer `payment.verify`. Credit application is Admin-only. Staff verification always awaits Admin review/authorization. Ensure old `purchase.record` or `purchase.review` grants cannot independently formalize acceptance. Review the applicability of the existing OR-list guard if any other route needs multiple actions.
4. Update future route descriptions, OpenAPI/DTO metadata and integration/unit expectations together. Test denied grant issuance and direct persisted legacy rows, revoked or stale sessions and retries, Admin authority for both paths, Staff with all unrelated grants, and preserved commission denial.
5. Technical deployments use separate infrastructure identities. O-13 deployment or emergency access conveys no application business actions. Audit deployment identity/version/time/outcome, constrain temporary access with scope, expiry and revocation, and test direct database and restore paths as separate controls. See the [deployment security contract](architecture-review.md#deployment-and-security).

## Saudi date and time contract

**M2-T03 / O-01/O-06/O-07/O-11.** Store business dates as PostgreSQL `date` and API `YYYY-MM-DD` values. Store actual events and materialized boundaries as `timestamptz` and serialize instants in UTC. Persist the applied `Asia/Riyadh` policy and original date inputs along with the boundaries. Parse dates as calendar values and convert explicitly in the studio timezone. Avoid host/browser local date constructors and implicit SQL session-timezone casts. Take one post-lock database wall-clock sample per decision and convert it explicitly to Riyadh. [PostgreSQL date/time types](https://www.postgresql.org/docs/17/datatype-datetime.html) · [PostgreSQL date/time functions](https://www.postgresql.org/docs/17/functions-datetime.html)

| Rule | Proposed representation and example |
|---|---|
| Immediate activation | Riyadh date of actual Admin activation is day one. Eligibility starts at the approval instant, so the first day may be shorter. The start date and activation timestamp are separate. |
| Future start | Validate a future local date and start at its Riyadh midnight. Never start from payment recording or verification. A 3-calendar-day membership starting on 12 November 2026 is valid through 14 November inclusive. The proposed exclusive end is 15 November 00:00 Riyadh, or 14 November 21:00 UTC. Compute with calendar-date arithmetic before conversion. |
| Suspension | Start at configured Riyadh midnight subject to recorded approval and valid lifecycle. The configured end date is proposed as the first resumption date, at its Riyadh midnight. Open-ended suspension has no automatic end. Reject ambiguous/backdated intervals until the transition contract defines them. |
| Private offer expiry | Proposed last acceptable local day equals stated expiry date, ending at exclusive next Riyadh midnight. Null means no date cutoff. Withdrawal and supersession remain authoritative. This boundary is a technical proposal, as is the stored representation of membership’s approved inclusive final day. |
| Installment overdue | Compare current Riyadh date with the effective due date. Overdue begins the day after it with an outstanding balance. Keep original and revised dates. |
| Reminders | Compute expiry/overdue windows, frequency, channel and monthly cap in Riyadh business time. Key each logical reminder by recipient, source, category, channel and intended Riyadh occurrence. Supersede stale schedules after due-date/expiry changes. Count and deduplicate atomically with outbox intent, distinguish required and optional categories, and reconcile uncertain SMTP delivery before retry. |

Use test cases on each side of local midnight, same date in different server timezones, inclusive final date, postponed start, expiry during suspension, and date revisions. Persisted applied boundaries preserve history if configuration or timezone data later changes.
